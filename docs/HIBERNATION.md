# RHEM 冬眠机制 v0.7.0

## 结论

`v0.7.0` 新增可选的 `HibernationManager`，默认关闭。它给运行期记忆补上生命周期治理：

```text
活跃
  → 长期无成功命中：观察期
  → 观察期继续无恢复：冬眠
  → 同类错误复发：立即唤醒
  → 冬眠足够久且人工批准：回收
```

冬眠不是删除。观察和冬眠都可以通过补丁回滚；回收必须人工批准，并继续使用现有删除补丁与回滚机制。

## 为什么需要冬眠

门控、蒸馏、反哺和阻尼分别处理收集、质量、归纳和稳定性，但记录仍可能“只进不出”：

- 长期没有成功命中的规则仍占用匹配空间；
- 已经失灵或环境漂移后的记录没有明确的退场路径；
- 直接删除会丢失“它为什么失效”的证据，也会失去环境回流后的复出机会。

冬眠把退场拆成可逆阶段：先观察，再低功耗待命，最后才由人决定是否回收。

## 状态机

| 状态 | 含义 | 默认行为 |
|---|---|---|
| `active` | 正常参与匹配与进化 | 保留当前行为 |
| `observing` | 长时间没有成功命中，开始收集失活证据 | 仍可匹配，只记录生命周期 |
| `hibernating` | 生命周期降权，规则禁用，等待复发或回收 | 不参与默认复扫；人工可查看和唤醒 |
| `active`（唤醒后） | 同类错误复发或人工确认后恢复 | 规则重新启用，保留历史记录 |
| 回收候选 | 冬眠超过阈值 | 只生成候选，不自动删除 |
| 已回收 | 人工批准后进入删除补丁 | 可通过补丁回滚恢复 |

默认阈值：

| 参数 | 默认值 | 含义 |
|---|---:|---|
| `observe_after_days` | `30` | 无成功命中多久后进入观察期 |
| `hibernate_after_days` | `30` | 观察期持续多久后进入冬眠 |
| `recycle_after_days` | `90` | 冬眠持续多久后成为回收候选 |

这些只是参考默认值，不是已经证明适合所有业务的最优阈值。

## 判据只读账本

`HibernationManager` 只读取：

- `distillation.hits`、`misses`、`consecutive_misses`；
- `last_hit_at`、`last_miss_at`、`last_feedback_at`；
- `scenario_sources`；
- 记录 `created_at`；
- 当前 `hibernation.status`、观察开始时间和冬眠开始时间。

它不调用 LLM，不推断业务语义，也不把“长时间没被调用”直接解释成“规则错误”。

## 唤醒

### 自动唤醒

显式传入 `hibernation=HibernationManager()` 后，`LearningEngine.ingest()` 会先检查同类错误是否回流：

- 识别错误按 `canonical` 匹配别名记录；
- 规则缺失按 `family` 或显式 `rule_key` 匹配规则；
- 知识缺口按 `term` 匹配词条。

命中观察期或冬眠期记录时，生成 `set_hibernation_state` 补丁并恢复为 `active`。规则仅在冬眠曾自动禁用它时恢复 `enabled=True`；人工原本禁用的规则保持禁用。

### 人工唤醒

```python
patch = engine.wake_hibernated(
    "rule",
    "rule:example",
    reason="人工确认环境回流",
    approver="徐应生",
)
```

人工唤醒也走补丁，可回滚回原来的观察期或冬眠状态。

## 计划与应用

先生成只读计划：

```python
plan = engine.hibernate(now="2026-09-12T00:00:00Z")
print(plan["summary"])
print(plan["recycle_candidates"])
```

确认后再执行观察和冬眠动作：

```python
applied = engine.hibernate(
    apply=True,
    actor="rhem:hibernation",
    now="2026-09-12T00:00:00Z",
)
```

`apply=True` 只执行 `observe` 和 `hibernate`，不会自动回收。回收需要单独的人工批准：

```python
patch = engine.recycle_hibernated(
    "alias",
    "old-alias",
    approver="徐应生",
)
```

如果当前记录还没有达到回收条件，`recycle_hibernated()` 会拒绝操作。

## 漂移样本

计划中的 `recycle_candidates` 和补丁中的 `hibernation_plan` 会保留：

- 领域、键、当前状态；
- 命中、失败、连续失败次数；
- 最后命中、最后失败和最后反馈时间；
- 场景覆盖数量；
- 空闲天数和观察/冬眠阶段天数；
- 回收资格时间。

这些字段是“规则如何消退”的可审计记录，可供后续人工分析或训练数据整理；当前参考实现不声称它们已经可以直接训练模型。

## 补丁与护栏

冬眠使用统一补丁治理：

- `set_hibernation_state`：记录观察、冬眠或唤醒状态；
- `delete_alias` / `delete_rule` / `remove_term`：人工批准后的回收；
- `hibernation_plan`：保存计划、状态判断和漂移样本；
- 回滚会恢复记录本体、`enabled` 状态和生命周期元数据。

护栏边界：

- 自动冬眠不得删除记录；
- 回收必须人工批准；
- 冬眠不冻结人工查看和人工唤醒；
- 当前生命周期降权不改蒸馏质量等级；规则通过 `enabled=False` 退出默认匹配；
- 冬眠不改变业务对错、规则条件、知识定义或护栏域；
- 参考实现不内置调度器，调用方可用人工任务或外部定时器执行计划。

## 已验证与未验证

当前测试验证：

- 默认不传 `hibernation` 时，旧流程不变；
- 观察期、冬眠期和规则禁用可以应用并回滚；
- 冬眠别名不会被视为已解决；
- 同类错误复发可以自动唤醒冬眠规则，且不会重新启用人工原本禁用的规则；
- 人工唤醒有补丁和审计元数据；
- 回收候选不会自动删除，必须通过人工批准；
- 回收补丁可以回滚恢复记录。

当前不声称：

- `30 / 30 / 90` 天阈值适合所有业务；
- 冬眠和唤醒一定降低生产维护成本；
- 空闲时间能够单独证明规则错误；
- 回收候选已经完成统计校准；
- 参考实现包含生产级定时调度、并发事务或权限系统。

## 六组件定位

冬眠是进化动力系统的“退场与复出”组件，与蒸馏形成两层治理：

- 蒸馏治“质量是否值得留”；
- 冬眠治“数量如何退出，以及退出后如何复出”。

它把失灵和漂移样本留在可审计的账本里，给后续的难例发掘与训练界提供第三类军粮入口。
