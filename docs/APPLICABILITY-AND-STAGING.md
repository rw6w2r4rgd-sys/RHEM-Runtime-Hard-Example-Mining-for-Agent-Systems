# 适用阶段与分工：为什么前期优先使用 RHEM

## 结论

RHEM 与难例发掘不是互相替代，而是处在不同阶段：

- RHEM 处理已经发生的运行期错误，把现场修正快速变成 Agent 可加载的记忆、规则或流程配置；
- 难例发掘利用积累起来的难例改进模型，争取把经验泛化到相似或未见的变体；
- 前期通常更需要“先让系统在真实运营里可用”，后期通常更需要“让模型从大量经验中形成更广的泛化能力”。

因此，前期优先采用 RHEM 的核心理由不是 RHEM 在所有方面都更强，而是：

> 此时最可靠、最有价值的知识，往往来自已经暴露的真实痛点、错误和现场修正。

## 前期面对的现实约束

在运营早期，团队常常同时缺少：

- 足够的训练样本；
- 稳定的高质量标注；
- 可代表真实长尾的评估集与回归集；
- 完成重训、评估、发版和再次验证所需的时间；
- 对业务全貌和未来输入分布的清晰认识。

但此时通常已经拥有：

- 真实运营中的具体错误；
- 领域人员知道的正确处置方式；
- 用户或操作员给出的纠错信号；
- 修复后可以快速观察是否解除当前问题。

这使早期成为一个很特殊的阶段：模型泛化能力还不够，但现场知识与错误信号已经开始出现。

## RHEM 在前期做什么

RHEM 把已出现的运营反馈组织成四类处置：

| 问题 | 运行期处置 | 主要收益 |
|---|---|---|
| 识别错误 | 加入别名、纠错映射 | 同类识别立即改善 |
| 流程错误 | 修改重试、超时、死锁检测等运行配置 | 不放任同类流程继续失控 |
| 规则缺失 | 决策器起草，人工批准后写规则 | 把专家判断变成可执行约束 |
| 知识缺口 | 上报未识别项，人工归因后写词条 | 把现场知识转成系统记忆 |

这些变更需要满足：

- 错误可观察、可归因；
- 同一问题有足够反馈，或人工提供可信修正；
- 自动变更生成补丁，可回滚、可复扫；
- 护栏域仍然禁止运行时改写。

RHEM 的目标不是让 Agent 第一天理解所有业务，而是让它在真实运行中更快减少重复错误。

## RHEM 不解决什么

RHEM 不是未卜先知，也不能替代模型训练和评估。

它不能：

- 处理从未出现且无法识别的未来错误；
- 在没有正确信号时自动判断什么是正确答案；
- 自动把局部规则泛化成模型级能力；
- 保证每条运行期规则都长期最优；
- 替代真实回归测试和线上评估。

RHEM 的预防是“同错复发预防”，范围窄但直接；难例发掘追求的是更广的泛化预防，但也不能保证所有未见情况都处理正确。

## 难例发掘在后期的位置

当以下条件逐渐具备时，难例发掘的价值会上升：

- 积累了大量带来源和处置结果的难例；
- 已经形成评估集、回归集和冲突检测；
- 有稳定的训练与发布管线；
- 运行期规则开始膨胀，需要提升模型内生能力；
- 希望覆盖更广的相似变体，而不是只避免已知错误复发。

此时 RHEM 的角色会从“主要修复机制”逐渐变成“数据前哨”：它持续产生带来源、带上下文、带处置结果的难例，为后续训练提供真实材料。

## 两条路线的分工

| 维度 | RHEM | 难例发掘 |
|---|---|---|
| 主要阶段 | 运营前期与持续运行期 | 训练与模型迭代阶段 |
| 输入 | 已发生的运行错误、用户纠错、验证信号 | 训练难例与标签 |
| 生效方式 | 运行期规则、记忆、流程补丁 | 重训、评估、发布 |
| 主要作用 | 避免已知错误复发 | 提升模型泛化能力 |
| 生效速度 | 相对重训发版路径更短 | 依赖训练与发布周期 |
| 主要边界 | 已知、可识别、可验证的问题 | 受数据、训练和评估质量限制 |
| 长期关系 | 为训练持续提供真实难例 | 把难例转成模型能力 |

## 对外表述边界

可以采用：

> 在运营前期，RHEM 利用已经发生的真实错误和现场修正，让可扩展 Agent 在缺少训练样本与评估闭环时先完成运行期适配；难例发掘则在后期利用这些积累，追求更广的模型泛化。两者互补。

不应采用：

- “RHEM 是所有 Agent 的最快方案”；
- “任何错误都能立即进入 Agent”；
- “RHEM 可以替代难例发掘”；
- “RHEM 已经被证明优于模型训练”；
- “概念绝对全球首创”。

## 一句话总结

> RHEM 管当下：让已经知道的错误尽快不再重复。难例发掘管未来：让积累的难例尽量变成更广的模型能力。前期先用 RHEM 站稳，后期再用难例发掘变强。
